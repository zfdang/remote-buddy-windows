# Windows 蓝牙遥控器信号处理分层架构总结

在 Windows 上接收蓝牙低功耗（BLE）遥控器的输入时，信号会从底层无线协议一路穿过系统蓝牙驱动、HID 子系统，最终到达桌面应用窗口。**不同层次看到的信号完整度、设备身份信息、独占拦截能力以及权限/侵入性代价完全不同**。

这也是为什么针对不同遥控器（如 Google Chromecast `G9N9N`、小米 `RC003`）和不同 Windows 版本（Windows 10 / 11），往往需要跨越多个层次做组合取舍，而不是靠单一 API 通吃所有按键与语音流。

---

## 一、从底层到应用层的五层信号模型

```text
[物理蓝牙遥控器]
   │
   ▼ (无线 BLE ATT / L2CAP)
┌─────────────────────────────────────────────────────────────────────────┐
│ 第 1 层：蓝牙核心传输与跟踪层 (BthPort.sys / HCI / L2CAP / ATT / ETW)   │
│  · 可见：原始 ACL 包、连接句柄 (0x0E01)、ATT Opcode 与句柄 (0x0029)      │
│  · 方案：BthPort ETW Event 402 (HCIRAW) / 过滤驱动                       │
└─────────────────────────────────────────────────────────────────────────┘
   │
   ▼ (UMDF HidOverGatt 驱动解包 GATT Report)
┌─────────────────────────────────────────────────────────────────────────┐
│ 第 2 层：用户态 HID-over-GATT 驱动层 (WUDFHost.exe / hidovergatt.dll)   │
│  · 可见：驱动内部的完整 HID 报告、宿主 PID、ContainerID / 蓝牙 MAC       │
│  · 方案：Frida / Frida Gadget Hook (备选未采用)                          │
└─────────────────────────────────────────────────────────────────────────┘
   │                                  │
   │ (私有服务直接交给 WinRT)         │ (标准 0x1812 HID 服务被系统接管)
   ▼                                  ▼
┌──────────────────────────────┐  ┌───────────────────────────────────────┐
│ 第 3 层：WinRT GATT API 层    │  │ 第 4 层：Windows HID 与原始输入层      │
│  · 私有服务(ATVV语音): 可直接 │  │  · 直接 HID 句柄 (HidDeviceReader)     │
│    读写与订阅，天然带蓝牙地址 │  │  · Win32 Raw Input (WM_INPUT / hDevice)│
│  · 标准 HID (0x1812):         │  │  · 系统会过滤/吞掉非常规 Usage 或保留 │
│    通常返回 AccessDenied      │  │    VKey=0xFF，仅监听无法直接拦截系统键 │
└──────────────────────────────┘  └───────────────────────────────────────┘
                                      │
                                      ▼ (OS 按键翻译与焦点分发)
                                  ┌───────────────────────────────────────┐
                                  │ 第 5 层：窗口与系统键盘消息层          │
                                  │  · WM_KEYDOWN / WM_APPCOMMAND / Hook   │
                                  │  · 已丢失物理设备来源，极易与本机键盘混 │
                                  └───────────────────────────────────────┘
```

## 二、各层次的能力边界与典型方案

### 第 1 层：蓝牙核心传输与 ETW 跟踪层（`BthPort.sys` / L2CAP / ATT）
- **能拿到什么信号**：
  蓝牙控制器与系统 `BthPort.sys` 交换的底层包（HCI Event、ACL 收/发数据包），再往里可以解析出 L2CAP CID `0x0004`（ATT 协议通道）中的 ATT 通知（如 `0x1B` Notification）、特征值句柄（如 G9N9N 的 `0x0029`、小米的 `0x0064`）与原始 HID 字节。
- **核心优势**：
  - **零进程注入**，属于微软官方开放的诊断跟踪机制；
  - 信号发生在 Windows HID 翻译器之前，因此**被系统键盘驱动吞掉的键也能看到**（例如小米 RC003 返回键 Usage `0xF1`、音量键 `0x80`/`0x81`，以及 G9N9N 的全量按键）。
- **天然短板与挑战**：
  1. **只有连接句柄，没有设备地址**：ACL 包头里的连接编号（例如 `0x0E01`）是临时会话句柄，需要宿主应用通过发送可识别的 GATT 查询（如随机 UUID 探针）把连接句柄绑定到具体的物理蓝牙地址。
  2. **不同 Windows 版本吐包行为不一致**：在部分 Windows 10 环境（如 `10.0.19045`）下，Event 402 可能正常输出入站 `AclReceived` 按键通知却省略出站 `AclSent` 探针包；另有部分系统或驱动场景可能出现只保留包头而裁剪载荷字节（脱敏）。
  3. **只读旁路**：可以读取原始按键，但无法阻断 Windows 下游继续产生系统按键响应；且通常需要管理员提权和启用 BthPort 敏感事件日志配置。

---

### 第 2 层：用户态 HID-over-GATT 驱动层（`WUDFHost.exe`）
- **能拿到什么信号**：
  Windows 用户态驱动框架宿主进程 `WUDFHost.exe` 加载的 `microsoft.bluetooth.profiles.hidovergatt.dll` 内部回调与设备复制 IOCTL（详见 [Frida Gadget HID 采集方案调研](frida-gadget-hid-tap-design.md)）。
- **核心优势**：
  - 处于 `BthPort` 与 Windows 键盘类翻译器之间的关键咽喉，既能拿到未经系统吞键的完整原始报告，又能直接从 PnP 注册表与驱动内存对象读取精确的 `ContainerID` 和蓝牙 MAC；
  - 在 IOCTL 复制点甚至可以在驱动把报告上报给系统前原地清空内容，从而**阻止触发系统原生键**（例如系统级截获与屏蔽）。
- **天然短板与挑战**：
  - 属于**高侵入性私有内存 Hook**，依赖未公开的微软 C++ 符号偏移、PDB 符号下载或大量版本哈希表；
  - 极易触发杀毒软件、Defender / EDR 或系统代码完整性策略拦截，生命周期管理复杂。**本项目仅作架构储备，现阶段不采用**。

---

### 第 3 层：系统 WinRT GATT API 层（`Windows.Devices.Bluetooth`）
- **能拿到什么信号**：
  通过公开 API `BluetoothLEDevice` 直接发现 GATT 服务、读写特征值与订阅通知。
- **核心优势与边界分化**：
  - **非系统独占的自定义服务（如 ATVV 语音服务）**：第 3 层是最佳选择——稳定、免提权、天然与目标设备蓝牙地址一对一绑定。Remote Buddy 两款遥控器的语音键控制（`StartSearch`/`AudioStart`/`AudioStop`）与 IMA ADPCM 音频流全部走这一层。
  - **标准 HID over GATT 服务（UUID `0x1812`）**：在 Windows 上通常由系统 HID 驱动独占保护，应用层用 WinRT 枚举/打开 HID Report 特征通常会直接被拒（`AccessDenied`），无法作为通用的普通按键采集来源。

---

### 第 4 层：Windows HID 类与原始输入层（直接 HID 读取 / Raw Input）
- **能拿到什么信号**：
  - **直接 HID 设备读写（`HidDeviceReader`）**：对未被键盘独占的 HID 集合（如部分消费控制集合）直接打开设备接口读报告；
  - **Win32 Raw Input（`WM_INPUT`）**：同时覆盖 `RIM_TYPEKEYBOARD`（系统已翻译的虚拟键码 VKey 和扫描码 MakeCode）与 `RIM_TYPEHID`（原始 HID 消费类报告），且每条消息附带物理设备句柄 `hDevice`，可通过设备路径中的 VID/PID、蓝牙地址或 `ContainerID` 做实体识别。
- **核心优势**：
  - **标准公开用户态接口**，无需管理员权限，无需驱动或系统敏感日志开关，延迟低、来源句柄清晰。
- **天然短板与挑战**：
  - **OS 翻译丢失**：对于键盘页非常规 HID Usage（如小米 RC003 的返回键 `0x00F1`、部分音量 Usage）或某些遥控器的全集报告（如测试环境下的 G9N9N），Windows 键盘类驱动可能不交付上层或返回 `VKey=0xFF`；
  - **无法拦截原生传递**：Raw Input 只是系统同时抄送给应用的只读事件流，无法阻止同一记按键继续被前台应用当成原生按键或触发系统功能（例如 `Win` / `Home` / `Sleep`）。

---

### 第 5 层：窗口输入消息与全局键盘钩子层（`WM_KEYDOWN` / `WM_APPCOMMAND` / Hook）
- **能拿到什么信号**：
  经过桌面窗口系统分发后的虚拟键码与多媒体命令（以及通过底层钩子做全局按键拦截/改键）。
- **核心边界**：
  - **无法直接分辨来自哪一台物理设备**（同一台电脑上本机键盘与多只蓝牙遥控器的按键会混在一起）；
  - 因此本项目的正式映射路由层**不从第 5 层识别遥控器来源**（物理归属必须留在第 1–4 层解决）。

---

## 三、五层能力对照总表

| 层次 | 代表技术 | 能拿到被系统吞掉的键吗？ | 如何绑定到指定物理遥控器 | 能否阻断原生按键传递 | 权限 / 系统风险 | 本项目采用定位 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **第 1 层：蓝牙核心/ETW** | BthPort ETW Event 402 | **能**（原始 ATT 通知字节） | 出站探针 UUID / 入站探针应答关联 ACL 句柄 | 否 | 需管理员开启跟踪；受不同系统 Event 402 实现影响 | **普通键主力／补齐路径**（G9N9N 主采；RC003 补抓返回与音量键） |
| **第 2 层：UMDF 驱动内部** | Frida / Gadget Hook `WUDFHost.exe` | **能**（最完整原始 HID 报告） | PnP 注册表 `HostPid` + MAC / `ContainerID` | **能**（可原地清零） | 高：注入系统进程、依赖私有偏移/PDB、易被杀软拦截 | **备选储备，暂不采用** |
| **第 3 层：WinRT GATT API** | `BluetoothLEDevice` / GATT 订阅 | HID (`0x1812`) 通常受阻；**私有服务全可见** | 直接绑定目标蓝牙对象 | 否（私有服务不会被 OS 当按键） | 低：微软官方第一方公开 API | **ATVV 语音键与麦克风音频唯一主力路径** |
| **第 4 层：HID / Raw Input** | `HidDeviceReader`、`WM_INPUT` | **部分不能**（依赖 OS 翻译与独占策略） | `hDevice` / 设备路径 / `ContainerID` | 否（仅只读监听） | 低：标准公开 API，无需提权 | **小米 RC003 标准普通键主力 + G9N9N 辅助验证** |
| **第 5 层：窗口与快捷键层** | `WM_KEYDOWN`、`WH_KEYBOARD_LL` | 不能（已被丢弃的键不会到达） | **无物理来源身份** | 全局 Hook 可做全局拦截 | 低～中（受 UIPI 权限边界约束） | **仅做向导局部交互辅助，不作为多遥控器归属依据** |

## 四、项目中的实际组合策略

理解这套分层模型后，很容易看清当前代码为什么采用“按信号与设备分层混合采集”：

1. **同一只遥控器同时走多个层次，并不矛盾**
   - **语音与麦克风（第 3 层）** 始终走公开的 WinRT ATVV 服务，最稳、不抢占、不依赖 ETW 是否工作；这也是为什么即使某个环境普通键失灵，语音键通常依然可用。
   - **普通按键（第 4 层为主 + 第 1 层补全/兜底）**：
     - 对 **小米 RC003**：大部分常用键系统翻译完好，走第 4 层 Raw Input 最稳；只把被系统吞掉的返回键与音量键下沉到第 1 层 ETW，并通过特征句柄 `0x0064` 白名单防止双重触发。
     - 对 **Google G9N9N**，BthPort ETW 是普通键的主要来源，直接 HID 和 Raw Input 是补充。看不到出站探测时，可以结合探测窗口内的入站应答与合法按键通知推断连接归属。没有入站应答时，兜底需在同一连接和属性上看到完整的按下、松开通知，且只有一个就绪设备符合解码条件。
2. **明确不跨越的技术边界**
   - 第 1 层（ETW）+ 第 3 层（WinRT）+ 第 4 层（Raw Input / Direct HID）全部使用微软公开支持的接口，**不注入第三方代码到 `WUDFHost.exe`**，不引入私有二进制偏移维护成本。
   - 当且仅当未来某代 Windows 系统更新彻底锁死了第 1 层 Event 402 的载荷交付且第 4 层也无法替代时，才依据 [Frida Gadget HID 采集方案调研](frida-gadget-hid-tap-design.md) 评估第 2 层的可行性。
